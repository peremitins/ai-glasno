> **Для исполнителей:** выполнять задачи строго в порядке этого документа. Один законченный этап включает реализацию, тесты и проверку; затем изменения остаются в рабочем дереве без создания коммита. Коммит после самостоятельного просмотра создаёт пользователь. Отправка в удалённый репозиторий выполняется только по отдельному запросу.

**Цель:** создать веб-приложение «Гласно» на React для проведения и разбора профессиональных диалогов по вакансии и профилю кандидата.

**Архитектура:** одностраничное React-приложение на Vite с модульной структурой. Синхронное клиентское состояние хранится в Redux Toolkit, асинхронные данные и кэш — в RTK Query. До подключения защищённого API используется типизированный mock API через MSW; ключи провайдеров и платёжные данные в браузер не передаются.

**Технологии:** React 19, TypeScript, Vite, React Router, Redux Toolkit, React Redux, RTK Query, MSW, React Hook Form, Zod, i18next, react-i18next, Tailwind CSS, shadcn/ui, Vitest, React Testing Library, ESLint и Prettier. React Compiler не подключается: оптимизацию через `useMemo`, `useCallback` и `React.memo` нужно применять осознанно и точечно.

## 3. Границы продукта

Приложение работает в современных браузерах и Telegram WebApp. Первичный язык интерфейса — русский; пользовательские строки хранятся в словаре локализации. При недоступности браузерных возможностей приложение показывает понятный текстовый сценарий вместо ошибки.

В состав первой версии входят:

- вход и демо-сессия пользователя;
- дашборд с краткой статистикой и быстрым стартом;
- создание сессии: вакансия, профиль, уровень, формат и настройки вопросов;
- проведение сессии: вопрос, ответ, таймер, подсказки, текстовый и голосовой ввод;
- история сессий и подробный отчёт;
- профиль, настройки и тарифный экран;
- каталог вопросов и страница вопроса;
- состояния загрузки, пустых данных, ошибок и отсутствующих разрешений браузера.

В первую версию не входят реальная оплата, хранение персональных файлов, отправка сообщений, вызовы AI-провайдеров из браузера и передача секретов в клиентский код.

## 5. Архитектура исходного кода

```text
src/
  app/                 # провайдеры, router, store, глобальные стили
  pages/               # компоненты маршрутов
  widgets/             # композиции для экранов: sidebar, dashboard, session workspace
  features/            # пользовательские действия и самостоятельные сценарии
  entities/            # типы и отображение: session, question, report, profile
  shared/
    api/               # RTK Query API, типы транспорта, обработка ошибок
    config/            # константы и публичные настройки
    lib/               # независимые утилиты
    ui/                # shadcn/ui и прикладные UI-элементы
  mocks/               # MSW handlers и согласованные тестовые данные
  i18n/                # конфигурация и словари локализации
  test/                # настройки тестовой среды и тестовые фабрики
```

Границы зависимостей: `pages` собирают `widgets` и `features`; `features` используют `entities` и `shared`; нижние слои не импортируют верхние. Компонент не обращается к сети напрямую: получение и изменение данных выполняются через хуки RTK Query.

## 6. Состояние и данные

### Redux Toolkit

Store содержит только синхронное клиентское состояние:

- `auth`: демо-сессия, статус входа и пользователь;
- `interview`: выбранные параметры, текущий ответ, статус этапа и таймер;
- `ui`: меню, модальные окна, уведомления и предпочтения отображения.

Состояние изменяется только reducer-ами `createSlice`; компоненты читают узкие selectors. Сложные последовательности действий оформляются в listener middleware или в отдельные функции feature-слоя, а не в JSX.

### RTK Query и mock API

RTK Query описывает endpoints для профиля, дашборда, сессий, отчётов, тарифов и каталога вопросов. MSW перехватывает запросы в режиме `mock`, возвращает типизированные ответы и моделирует задержку, пустой результат и прикладную ошибку. В режиме интеграции базовый URL берётся только из `VITE_API_BASE_URL`.

Каждый endpoint имеет типы входа и ответа, понятные tag types для invalidation и обработку состояний `isLoading`, `isFetching`, `isError` и `data` в интерфейсе.

## 7. Формы, разрешения и доступность

- Все формы используют React Hook Form и Zod; сообщения валидации локализованы.
- Для микрофона, камеры и полноэкранного режима предусмотрена проверка доступности API через `typeof` и отдельный UI для отказа в разрешении.
- Голосовой ввод имеет обязательный текстовый fallback.
- Интерактивные элементы доступны с клавиатуры, имеют корректные aria-атрибуты и видимый фокус.
- Цвета определяются CSS-переменными и токенами Tailwind; контраст и уменьшение анимаций учитываются через системные предпочтения.

## 8. Безопасность

- В репозитории не хранятся реальные токены, приватные ключи, персональные данные и ответы внешних сервисов.
- В клиентский код не добавляются ключи AI-провайдеров, relay-секреты или секреты платежей.
- `.env` не коммитится; в `.env.example` допускаются только имена публичных переменных без значений.
- Любая будущая защищённая интеграция выполняется через серверный API, а не из браузера.

## 10. Правила коммитов

Коммит создаёт пользователь после законченной и проверяемой задачи. Он содержит одну связанную цель, не смешивает рефакторинг с новой функцией и пишется на русском в формате:

```text
тип: краткое действие в повелительном наклонении
```

Допустимые типы: `feat`, `fix`, `refactor`, `test`, `docs`, `chore`. Агент не создаёт и не отправляет коммиты; отправка в удалённый репозиторий выполняется только по явному запросу.

### Правила именования веток

Имя ветки состоит из рабочего префикса и короткого описания в kebab-case:

```text
<префикс>/<краткое-описание>
```

- `features/` — новая пользовательская возможность;
- `bugfix/` — обычное исправление дефекта, которое проходит стандартный путь разработки;
- `hotfix/` — срочное исправление для production, которое направляется в обход `development`.

Служебные префиксы инструментов и исполнителей, включая `codex/`, `claude/` и `ai/`, не используются. Правило относится к веткам; для сообщений коммитов сохраняются типы из раздела выше.

Каждая новая задача выполняется в отдельной ветке, созданной до первого изменения кода. В имени не используются номера задач, слово `task` и хеш-коды: например, `features/interview-workspace`. Ветку разрешено слить в целевую только после явного согласования пользователя; до этого изменения остаются изолированными в ветке.

## 11. Конфигурация агентской среды

- `AGENTS.md` — общие правила для автоматизированной разработки, безопасность, архитектура и порядок коммитов.
- `CLAUDE.md` и `.claude/settings.json` — правила Claude Code и hooks для Serena.
- `.claude/agents/i18n-sweeper.md` — узкий read-only агент для контроля пользовательских строк после подключения i18next.
- Codex использует общий локальный MCP-конфиг Serena; проектные инструкции читает из `AGENTS.md`.

Узкие read-only задачи выполняются минимальным доступным effort. Сложные изменения сначала ограничиваются точным поиском, проверкой references и чтением только затронутых модулей. Для служебной генерации используются активные подписочные сессии, а не ключи runtime-функций приложения.
